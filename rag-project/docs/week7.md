## 과제 성격의 변화 (중요)

이번 주부터 과제 방식이 바뀌었다.

- **단발성 과제 없음.** 매주 배운 내용을 **내 개인 프로젝트에 직접 적용해 고도화**하는 형태로 통합됐다.
- 즉, 이번 주 위클리 챌린지 = 내 RAG 프로젝트를 LangChain + FastAPI + LangSmith로 한 단계 끌어올리는 작업 그 자체다.
- 따라서 "과제용 코드"와 "내 프로젝트"를 따로 만들 필요 없다. **내 프로젝트 하나를 키운다.**

> 내 프로젝트 컨셉: **AI 학습 코파일럿** (arXiv LLM/RAG 논문 50~100편 + HF/PyTorch docs + 내 학습노트 기반 Agentic RAG). 이번 주는 그 Phase 1(텍스트 RAG)의 엔진을 프레임워크 위로 옮기는 단계.

### 학습·개발 우선순위 (강사님 명시 — 필독)

자기 모델(커스텀 모델) 개발에 몰두하다 본 진도를 놓치는 사람이 많아, 강사님이 우선순위를 못박으셨다.

| 순위 | 할 것 | 비고 |
|---|---|---|
| **1순위 (최우선)** | LangChain(7주차)·LangGraph(8주차) 기반 **에이전트 개발 역량** | 모든 역량을 여기 집중 |
| **2순위** | 프레임워크 없는 **바닐라 RAG 복습** | 기본기 |
| **3순위 (선택)** | **자기 모델 개발** | 지금 성능 안 나오는 게 정상. **잠정 중단**하고 9주차 튜닝 때 다시. |

- **기본 엔진은 자기 모델이 아니다.** 프론티어 모델(Gemini 1.5 Flash 등)이나 쓸만한 로컬 모델(Gemma 2B 등)로 구현할 것.
- 7주차부터 별도 미니 과제 없음 → **오직 '개인 프로젝트' 하나를 계속 제출·고도화.** 과제 미제출 = 개인 프로젝트를 안 하고 있다는 뜻.

## 멘탈 관리 — "지나간 버스는 잊어라"

강사님이 따로 시간을 들여 강조하신 부분.

- 마음가짐: **"7주차부터 내 개인 프로젝트를 LangChain RAG로 처음부터 새로 시작한다."**

> 핵심: 바닐라 RAG가 미완성이어도 괜찮다. LangChain 버전을 새 출발점으로 삼으면 된다.

## 과제 1 — LangChain 기반 RAG 마이그레이션 (필수)

### 무엇을 하는가

기존 **바닐라 RAG**(프레임워크 없이 순수 파이썬으로 직접 짠 RAG)를 **LangChain 프레임워크를 쓰는 구조로 변환(마이그레이션)**한다.

### ⚠️ 강사님 특별 주의사항 — 형상 관리

이 부분을 가장 강조하셨다.

- **덮어쓰기 절대 금지.** 바닐라 RAG 코드를 LangChain 코드로 덮어써서 날려버리면 안 된다.
- **버전 보존 필수.** 면접관이 *"바닐라 RAG는 어떻게 구성했나요?"* 물으면 **즉시 보여줄 수 있어야** 한다.
- **관리 방법:**
  - Git **브랜치(Branch)**를 따거나 **태그(Tag)**를 단다.
  - Git이 어려우면 **새 저장소를 파거나 폴더를 분리**해서 바닐라 / LangChain 버전이 각각 독립 보존되게 한다.

```
# 예시 — 태그로 바닐라 시점 박제 후 브랜치에서 작업
git add . && git commit -m "vanilla RAG 완성 시점"
git tag vanilla-rag-v1
git checkout -b langchain-migration

# 또는 폴더 분리
project/
├── vanilla_rag/      ← 손대지 않고 보존
└── langchain_rag/    ← 이번 주 새로 작성
```

### 마이그레이션이 실제로 뜻하는 것

바닐라에서 내가 직접 함수로 짰던 단계들을 LangChain의 표준 컴포넌트로 교체하는 것:

| 바닐라 (직접 구현) | LangChain 컴포넌트 |
|---|---|
| PDF/텍스트 직접 파싱 | Document Loader |
| 직접 짠 청킹 함수 | Text Splitter |
| 임베딩 API 직접 호출 | Embeddings |
| 벡터 저장/검색 직접 관리 | VectorStore + Retriever |
| f-string으로 프롬프트 조립 | PromptTemplate |
| LLM API 직접 호출 | LLM / ChatModel |
| 응답 후처리 직접 | Output Parser |

이 컴포넌트들을 **LCEL(파이프 `|` 연산자)**로 엮어 하나의 체인으로 만든다.

```python
# 개념 스케치 (LCEL)
chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)
answer = chain.invoke("RAG에서 청킹 전략이 왜 중요해?")
```

> **내 프로젝트 적용 포인트:** 청킹 시 **figure 캡션 메타데이터 보존**, 답변에 **출처·신뢰도 표기**를 처음부터 넣을 것. (Phase 2 멀티모달이 먹기 좋은 구조 + 주니어 변별 신호)

### 왜 LangChain으로 옮기나 (면접 대비 논리)

- 컴포넌트 교체가 쉬워진다 (벡터DB·LLM 갈아끼우기).
- LangSmith·평가·에이전트(LangGraph) 등 생태계와 자연 연결된다.
- 단, **"바닐라로도 짤 줄 알지만 생산성/생태계 때문에 LangChain을 택했다"**는 서사가 강하다 → 그래서 바닐라 버전 보존이 중요.

## 핵심 설계 원칙 — 인덱싱 ↔ 생성 라이프사이클 분리

> 과제 1과 2를 잇는 가장 중요한 설계 포인트. 강사님이 초보자가 가장 많이 하는 실수로 지목하셨다.

RAG는 두 단계로 나뉜다.

| 단계 | 하는 일 | 언제 실행? |
|---|---|---|
| **인덱싱 (Indexing)** | 문서 로드 → 청킹 → 임베딩 → 벡터DB 적재 | **딱 한 번** (또는 자료 갱신 시) |
| **생성 (Generation, RAG)** | 검색 → 프롬프트 조합 → LLM 답변 | 사용자 요청마다 |

**흔한 실수:** 스크립트 실행/API 요청 때마다 문서를 다시 로드·임베딩하는 것. 이러면 요청 한 번마다 수 초 + **막대한 임베딩 API 비용 + 메모리 낭비**가 터진다.

→ **인덱싱은 미리/한 번만 끝내두고, 요청 때는 검색·생성만** 한다. (이걸 FastAPI에서 구현하는 게 아래 Lifespan)

> **내 프로젝트 적용 팁 (강사님 추천):** 수업에서 배운 걸 내 언어로 정리한 **마크다운 서브노트/TIL 문서**를 **Directory Loader**로 일괄 로드해 인덱싱 재료로 쓰면 훌륭하다. 내 학습노트 코퍼스 컨셉과 정확히 맞는다.

## 과제 2 — FastAPI 래핑 (필수)

### 무엇을 하는가

새로 만든 **LangChain RAG 체인을 FastAPI로 감싸서(Wrapping)** 외부에서 호출 가능한 **REST API 서버**로 만든다.

### 실무적 관점 (강사님 조언)

- 이건 **교재에 정답·튜토리얼이 친절하게 나와있는 내용이 아니다.**
- **스스로 고민해서 푸는 실전 도전 과제**다. 막히는 게 정상.

### 최소 구현 형태

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Query(BaseModel):
    question: str

@app.post("/ask")
def ask(q: Query):
    answer = chain.invoke(q.question)   # 과제 1에서 만든 체인 호출
    return {"answer": answer, "sources": [...]}   # 출처 함께 반환
```

### Lifespan — 서버 시작 시 인덱싱 1회 (핵심)

위 '인덱싱↔생성 분리' 원칙을 FastAPI에서 구현하는 방법. **Lifespan**(`@asynccontextmanager`)은 앱이 요청을 받기 **시작하기 전 단 한 번만** 실행되는 초기화 훅이다. 여기서 인덱싱·체인 구성을 끝내고 `app.state`에 체인을 저장해두면, 요청마다 무거운 작업을 반복하지 않는다.

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 서버 부팅 시 단 한 번: 인덱싱 + 체인 구성
    app.state.chain = build_rag_chain()   # 벡터DB 로드/검색기·프롬프트·LLM 결합
    yield
    # (필요시 종료 정리 로직)

app = FastAPI(lifespan=lifespan)

@app.post("/ask")
def ask(q: Query):
    answer = app.state.chain.invoke(q.question)
    return {"answer": answer, "sources": [...]}
```

### 왜 GET이 아니라 POST인가

질문 하나만 받더라도 **POST로 설계**할 것. 향후 사용자 ID·부가 메타데이터 등 복잡한 JSON 요청이 들어올 것에 대비하는 게 실무 관행이다.

### 스스로 고민할 것

- 요청(Request)에 무엇을 담을까? (질문만? top_k 같은 옵션도?)
- 응답(Response)에 무엇을 내려줄까? (답변 + **출처** + 신뢰도?)
- 에러 처리 (검색 결과 0건, LLM 호출 실패 등)
- 스트리밍 응답을 줄 것인가? (선택)

> **내 프로젝트 제약 (메모리 기준):** API 키는 **Colab Secrets**로 관리(하드코딩 금지). **FastAPI 개발/디버깅은 로컬**에서, Colab은 GPU 서빙(ngrok)용으로만.

## 과제 3 — LangSmith 추적 및 평가 (필수)

### 무엇을 하는가

구축한 LangChain 앱의 **내부 실행 과정, 토큰 사용량, 프롬프트 입출력**을 추적·모니터링하기 위해 **LangSmith**를 연동한다. 더불어 **Dataset 기반 평가**까지 수행한다.

두 가지 축:

1. **Tracing (추적):** 체인이 한 번 돌 때 retriever가 뭘 가져왔고, 프롬프트에 뭐가 들어갔고, LLM이 토큰 몇 개를 썼는지 단계별로 들여다본다.
2. **Evaluation (평가):** 질문-정답 쌍을 모은 **Dataset**을 만들어, 체인을 자동으로 돌리고 품질을 점수화한다.

> **왜 필요한가 (옵저버빌리티 ≠ 로깅):** 에이전트 시스템은 로직 실행을 LLM이 한다 → 코드만 봐선 내부를 모르는 **블랙박스**다. `print` 문으로는 "어떤 문서를 찾아 어떤 프롬프트를 조합했는지" 추적이 거의 불가능. 그래서 전용 관찰 도구가 필수다.

**추적 구조:** 하나의 큰 체인 실행 = `Trace`, 그 안의 세부 단계 = `Run`, 더 잘게 = `Span`. 웹 UI에서 각 단계의 지연 시간·입출력을 시각적으로 본다.

### ⏰ 수행 시점 안내

- LangSmith 연동/활용법은 **이번 주 강의 후반부(수요일 등)**에 상세히 다룬다.
- **수업 진도를 다 들은 뒤** 개인 프로젝트에 적용하면 된다. (지금 미리 막혀서 헤맬 필요 없음)

### 연동은 거의 환경변수 수준

```python
import os
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "..."   # Colab Secrets로
os.environ["LANGCHAIN_PROJECT"] = "ai-study-copilot"
# 이후 LangChain 체인을 실행하면 자동으로 LangSmith에 기록됨
```

### Dataset 기반 평가 흐름

```
1. 평가용 질문-정답 쌍 수집 (내 논문 코퍼스 기준 Q&A)
2. LangSmith에 Dataset으로 업로드
3. 체인을 Dataset 전체에 대해 실행
4. Evaluator로 채점 (정확성 / 관련성 / 출처 적절성 등)
5. 결과 비교 → 어떤 청킹·프롬프트가 더 나은지 판단
```

채점 방식은 **LLM-as-a-Judge**(다른 LLM이 모범답안과 비교해 0~1점) 또는 **휴리스틱**.

### ⚠️ 올바른 평가 전략 (강사님 강조)

- **심판은 선수보다 똑똑해야 한다.** 내 모델이 가벼운 모델(Gemini 1.5 Flash, Gemma)인데 같은 급을 Judge로 쓰면 '팔이 안으로 굽는' 편향이 생긴다. Judge는 **현존 최고 성능 프론티어 모델(GPT-4o, Gemini 1.5 Pro 등)**을 써야 공정하다.
- **사람이 직접 평가하려면 그 도메인 전문가여야 한다.** 답변 품질을 제대로 판단할 수 있어야 제대로 된 평가 데이터셋이 나온다. (내 경우 = arXiv 논문 내용을 내가 충분히 이해하고 있어야 모범답안을 만들 수 있음)

### ⚠️ 프롬프트 관리 기능은 지양 (락인 경계)

LangSmith는 프롬프트를 코드에서 분리해 웹에서 관리하는 기능도 제공하지만, **이건 쓰지 말 것**을 권하셨다.

- 웹에서 프롬프트 수정·즉시 배포 → 책임 소재상 위험, **피어 리뷰(PR) 불가능**.
- 지나치게 의존하면 다른 도구로 갈아타기 힘든 **락인(lock-in)** 발생.
- **관찰(Tracing) 용도로만** 쓰고, 프롬프트는 코드(Git)에 두자.

> **내 프로젝트 연결:** 6주차에 정리한 **RAGAS**(faithfulness, answer relevancy, context precision/recall)와 묶어서 보면 "평가를 1급 시민으로 취급"하는 서사가 완성된다. LangSmith로 추적, RAGAS/LangSmith Evaluator로 점수화.

## ⚠️ 보안 & 실무 함정 (꼭 점검)

- **API 키 유출 = 대참사.** `.env`를 **`.gitignore`에 반드시 추가**하고 푸시 전 두세 번 점검. 실수로 키를 GitHub에 푸시하면 크롤링 봇이 즉시 탈취 → 과거 **AWS가 계정을 한 달간 잠가(Suspend) 파이널 프로젝트가 강제 중단된 사례**가 있었다. (내 제약: 키는 Colab Secrets로 관리)
- **`dotenv` ❌ → `python-dotenv` ⭕.** `pip install dotenv`는 업데이트 끊긴 구버전(0.9.9)이 깔린다. 반드시 `pip install python-dotenv` 설치 후 코드에선 `from dotenv import load_dotenv`.
- **LangSmith에 트레이스가 안 보일 때:** 대시보드 좌측 상단 **앱 필터가 특정 앱에 고정**돼 있을 수 있다 → **'All'**로 바꾸면 전체 기록이 보인다.
- **디렉토리 구조:** 남의 잘 짜인 GitHub(`src/`, `models/`, `utils/` 분류 등)를 관찰하고, 취향이 없으면 잘 된 구조를 포크 떠서 모방하는 것부터 시작.

## 코드 문해력 — AI가 짠 코드를 내 저장소에 올릴 때

AI에게 코드를 짜게 하는 것 자체는 문제없다. 문제는 **이해 못 한 채 GitHub에 올리는 것**. (참고문헌 환각을 검증 안 해 Desk Reject 당하는 논문과 같은 실수)

- **주석 포함 한 글자도 빼놓지 말고 다 읽어라.** 내 저장소에 올릴 코드라면 필수.
- 잘 돌아가도 **왜 그렇게 동작하는지 모르면 그냥 넘어가지 말 것.** Claude/ChatGPT에게 "이 코드는 왜 이렇게 되냐" 집요하게 추궁해 완벽히 이해 → 직접 타이핑 안 해도 **코드 검증 능력(문해력)**이 실력으로 남는다.
