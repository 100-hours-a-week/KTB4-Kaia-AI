# 7주차 회고

> 코드를 짜는 것보다 제약 안에서 어떤 선택을 해야 하는지 판단하는 시간이 훨씬 길었다. 이 문서는 무엇을 만들었는지가 아니라 왜 그렇게 만들었고, 무엇이 어려웠고, 무엇을 배웠는지를 다룬다. 프로젝트 소개·기술 스택·사용법은 [README](../README.md) 참고.

---

## 1. 무료 티어 제약

RAG 구현 자체보다 어려웠던 건 제약 조건 안에서 어떤 선택을 해야 하는지 판단하는 것이었다. 이번 주에 벽을 세 번 만났다.

### 1-1. Gemini 임베딩 일일 할당량

문서 인덱싱을 조금만 반복해도 무료 한도가 거의 소진됐다. 좋은 API 임베딩 모델을 쓰고 싶었지만, 재실험이 불가능하면 개선도 불가능하다는 걸 알게 됐다. 결국 로컬 임베딩 `BAAI/bge-m3`으로 전환했다 — 성능보다 계속 실험할 수 있다는 쪽이 더 중요했다.

### 1-2. Chroma Cloud 300 레코드 제한

문서 청크가 478개라 클라우드 무료 한도를 초과했다. 처음엔 클라우드가 더 나은 선택이라 생각했는데, 이 프로젝트 규모에서는 `PersistentClient`(로컬 영속 저장)가 더 맞았다. 서버 비용도 없고, 재실행해도 인덱싱을 다시 안 해도 된다.

### 1-3. Judge 모델 선택

이상적으로는 생성 모델보다 강한 모델이 평가해야 하는데, `gemini-2.5-pro`는 무료 티어에서 limit:0이라 호출 자체가 안 됐다. Flash를 Judge로 쓸 수밖에 없었고, 이 한계는 4절 평가 결과에 그대로 적어뒀다.

세 문제 다 정해진 정답이 없었다. 제약과 측정으로 선택을 정당화하는 과정이 이번 주의 가장 큰 공부였다.

## 2. 검색 실패 디버깅 — Q3

"이미지 분류의 주요 과제는 무엇인가?" 질문에 모델이 계속 "자료에서 확인할 수 없습니다"라고 답했다. 정답("Challenges" 섹션)은 분명히 코퍼스 안에 있었는데도.

처음엔 `k`(검색 문서 수) 문제라 생각해 3→5로 늘렸는데 그래도 안 잡혔다. LangSmith Trace로 retriever가 실제로 가져오는 청크를 확인해보니 k 문제가 아니라 청킹 문제였다.

**원인:** CS231n 노트가 일부 섹션 제목을 `**Challenges**`처럼 볼드로 쓰고 `#` 헤더로 안 써서, Markdown Header Splitter가 이 섹션을 분리하지 못했다. 긴 섹션을 길이 기준으로 재분할하면서 뒤쪽 청크는 어떤 섹션인지 맥락 자체가 사라진 것도 원인이었다.

**해결:** 헤더 경로를 서브청크 앞에 다시 주입하는 `_inject_header_context`를 만들었다.

```
Image Classification
└── Challenges
```

이렇게 상위 맥락을 포함시키니 retriever가 정답 섹션을 잡기 시작했다. 검색 품질이 모델 자체보다 데이터 구조에 더 좌우된다는 걸 이번에 체감했다.

## 3. API 설계

FastAPI로 감싸는 건 튜토리얼에 정답이 없는 부분이라 실제로 막혔다.

처음엔 요청마다 체인을 새로 만들고 있었다. 느리고, 임베딩 비용이 요청마다 발생하고, 구조도 나빴다. 정리한 방식은 이렇다.

- **`lifespan`에서 체인 1회 구성:** 서버 시작 시 `build_rag_chain()`을 한 번만 호출해 `app.state.rag`에 보관. 요청마다 인덱싱을 반복하지 않는다.
- **`build_rag_chain()` 캡슐화:** 평가 스크립트(`baseline.py`)와 API 서버가 같은 체인을 쓰게 했다. 평가와 서빙이 다른 로직이면 점수가 실제 품질을 보장하지 못한다.
- **레이어 분리:** `routers/ask.py`(입력 검증) → `controllers/rag.py`(에러 변환) → `rag.py`(엔진).
- **POST 엔드포인트:** 질문 하나지만 향후 top_k·사용자 메타데이터 등 복잡한 요청에 대비.
- **출처 반환:** `RunnableParallel`로 검색을 1회만 수행해 답변 생성과 출처 추출이 같은 결과를 공유.

## 4. LangSmith 추적 + 평가

`cs231n-rag-eval` Dataset(핵심 개념 Q&A 5쌍)으로 세 지표를 측정했다.

| 지표 | 의미 |
|---|---|
| `keyword_recall` | 기대 답변의 핵심 내용어 회수율 (휴리스틱) |
| `llm_judge_semantic_match` | 기대 답변과의 의미 일치도 (LLM Judge) |
| `answer_relevancy` | 질문에 직접 답하는지 (LLM Judge) |

**청킹 개선 전후**

| 버전 | 설정 | keyword_recall | llm_judge | answer_relevancy |
|---|---|---|---|---|
| v1 | k=3 | 0.33 | 0.50 | — |
| v1.1 | k=5 | 0.36 | 0.60 | — |
| v2 | 마크다운 청킹 + 헤더 주입 + bge-m3 | 0.37 | **0.90** | 0.90 |

청킹과 임베딩 개선으로 llm_judge가 0.60 → 0.90로 뛰었다. 계속 0점이던 Q3("이미지 분류의 주요 과제")도 해결됐다.

**생성 모델 비교** (같은 검색·같은 Judge, 생성 모델만 교체 — [LangSmith 비교 뷰](https://smith.langchain.com/o/89ea1ae3-97f2-4b64-a21f-25194d654042/datasets/8de463c5-e289-435c-9274-9e4a2898e773/compare?selectedSessions=7a005b61-ba8a-4361-991d-a87c83a248cd%2Ca7bbac05-02ff-4955-94cd-1d0ff82f4caf&source=7a005b61-ba8a-4361-991d-a87c83a248cd&textDisplayMode=full))

| 생성 LLM | keyword_recall | llm_judge | answer_relevancy | latency(P50/P99) | 추정 비용(5문항) |
|---|---|---|---|---|---|
| gemini-2.5-flash (API) | 0.37 | 0.90 | 0.90 | 8.5s / 29.5s | $0.0101 |
| gemma4:e4b (로컬) | 0.37 | 0.90 | 1.00 | 27.8s / 40.2s | $0 |

로컬 모델이 품질은 Gemini와 동급(관련성은 오히려 높음), 트레이드오프는 속도(P50 기준 약 3배)뿐 — 단, 문항마다 편차가 크다.

| 문항 | gemini latency / 추정 비용 | gemma latency |
|---|---|---|
| Q1 Conv vs FC layer | 5.4s / $0.0020 | 35.8s |
| Q2 ResNet 혁신 | 2.6s / $0.0009 | 22.4s |
| Q3 이미지 분류 과제 | 29.5s / $0.0018 | 27.8s |
| Q4 배치 정규화 역할 | 8.6s / $0.0018 | 24.2s |
| Q5 역전파 그래디언트 계산 | 8.5s / $0.0036 | 40.2s |

Q3는 두 모델 다 유독 느렸고(둘 다 30초 안팎), Q5는 gemini 0.684 → gemma 0.632로 로컬 모델이 오히려 낮았다. P50/P99 같은 집계 숫자 뒤의 문항별 트레이드오프까지 봐야 한다는 게 결론이다.

> 위 "비용"은 실제 청구액이 아니라 LangSmith가 토큰 수 × 모델별 정가로 추정한 값이다. 무료 티어라 실제로 낸 돈은 없다.

**평가 한계:** Judge는 답변 생성 모델보다 강해야 편향이 없는데, `gemini-2.5-pro`는 무료 티어 limit:0이라 호출이 안 돼 Flash를 그대로 Judge로 썼다. billing을 켜면 분리할 수 있다.

## 5. 배운 것 & 다음 주

이번 주 전까지 RAG를 Loader → Splitter → Embedding → Retriever → LLM 정도로만 이해했는데, 실제로는 제약 조건 파악 → 설계 → 측정 → 개선을 반복하는 엔지니어링 문제라는 걸 배웠다.

평가가 있으니 무엇이 더 나은지 점수로 판단할 수 있다는 게 이전과 가장 달랐다. 감으로 판단하던 걸 LangSmith 트레이스와 Dataset 점수로 구체적으로 볼 수 있게 됐다.

**다음 주:** 리랭커(Q3류 직격), RAGAS 평가 도입, 코퍼스 확장, LangGraph 기반 Agentic RAG로 확장.
